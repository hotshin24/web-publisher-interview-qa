PART 1개인·경력·직무전환

Q1. 1분 자기소개를 해주세요.

안녕하세요. 커머스와 디자인 실무 경험을 기반으로 웹퍼블리셔로 직무를 전환한 신호진입니다.

신발 상품기획과 디자인, 온라인 쇼핑몰, 콘텐츠기획, 편집디자인 업무를 경험했고, 편집디자인 업무 중 WordPress 홈페이지를 직접 제작하고 운영하면서 웹 구현에 관심을 갖게 됐습니다.

이후 HTML, CSS, JavaScript, jQuery를 학습했고, JW Anderson 이커머스 프로젝트에서 392페이지 규모의 정적 사이트를 직접 퍼블리싱했습니다. 완성 후에는 CSS 구조를 다시 분석해 15,208줄을 8,812줄로 줄이는 리팩터링을 진행했습니다.

최근 HOOT UP 프로젝트에서는 AI가 생성한 164페이지 산출물을 검수하면서 359건의 문제를 기록하고 수정했습니다. 디자인을 이해하면서 구현할 수 있고, 결과물을 끝까지 검수하는 것이 제 강점입니다.

Q2. 왜 40대에 웹퍼블리셔로 전향했습니까?

완전히 다른 분야로 갑자기 이동했다기보다, 제가 해오던 일이 점차 웹으로 확장됐다고 생각합니다.

상품디자인에서는 사양서를 만들고 생산 결과를 검수했고, 쇼핑몰에서는 상품과 구매 동선을 경험했고, 편집디자인에서는 수백 페이지의 정보를 일정한 규칙으로 관리했습니다. 그러다 WordPress로 회사 홈페이지를 직접 만들면서 디자인 결과물이 브라우저에서 실제로 동작하는 과정에 흥미를 느꼈습니다.

그래서 기존 디자인 경험을 버리는 것이 아니라 HTML, CSS, JavaScript라는 구현 능력을 추가하는 방향으로 전환했습니다.

Q3. 43세 신입인데 왜 우리 회사가 뽑아야 합니까?

웹퍼블리싱 실무 경력만 보면 저는 주니어입니다. 그 점은 인정합니다. 대신 사회생활 전체가 처음인 신입과는 다르게 일정, 품질, 납기, 협업, 결과물 검수에 대한 경험이 있습니다.

이전에는 중국 생산 현장에서 샘플과 양산품을 비교했고, 편집디자인에서는 수백 페이지 문서의 일관성을 관리했습니다. 지금은 같은 방식으로 웹 결과물의 오류와 일관성을 검수하고 있습니다.

나이 자체를 장점이라고 주장하기보다, 기존 경험을 웹 업무에 얼마나 빠르게 전환할 수 있는지를 결과물로 보여드리고 싶습니다.

Q4. 어린 팀장이나 사수 밑에서도 일할 수 있습니까?

네. 연령과 해당 직무의 숙련도는 별개라고 생각합니다. 웹퍼블리싱 경력이 저보다 많은 분이라면 배우는 것이 당연합니다.

이전 직급을 현재 직무에 그대로 적용하려는 생각은 없고, 제가 가진 디자인·커머스 경험이 도움이 되는 부분에서는 적극적으로 기여하되 웹퍼블리싱 실무는 배우는 자세로 일하겠습니다.

Q5. 이전 직급보다 낮은 직급으로 입사해도 괜찮습니까?

괜찮습니다. 이전 직급은 이전 직무에서의 경험에 대한 것이고 웹퍼블리셔 경력과 동일하다고 생각하지 않습니다. 새로운 직무에서는 새로운 기준으로 평가받는 것이 맞다고 생각합니다.

Q6. 이전 연봉보다 낮아질 수 있는데 괜찮습니까?

직무 전환 과정이라는 점을 알고 있기 때문에 이전 직급과 연봉을 그대로 요구하는 것은 현실적이지 않다고 생각합니다. 다만 역할, 회사의 급여 체계, 기대 수준을 기준으로 합리적으로 협의하고 싶습니다.

Q7. 왜 이전 일을 계속하지 않았나요?

기존 경험 자체는 의미 있었지만 앞으로 어떤 역량을 중심으로 커리어를 쌓을지 고민했습니다. 디자인 결과물을 만드는 것에서 더 나아가 실제 웹 화면을 구현하고 유지하는 업무가 제 성향과 더 잘 맞는다고 판단해 전환했습니다.

Q8. 웹퍼블리셔를 얼마나 오래 할 생각인가요?

단기간에 다른 직무로 이동하기 위한 과정으로 생각하지 않습니다. 우선 웹퍼블리싱 실무 경험을 충분히 쌓고 HTML, CSS, JavaScript 기반 UI(사용자 인터페이스) 구현 역량을 깊게 만드는 것이 현재 목표입니다.

Q9. 프론트엔드 개발자로 갈 생각 아닌가요?

JavaScript 역량은 계속 확장하고 싶지만 현재 지원하는 역할은 웹퍼블리셔입니다. 지금 제 강점과 포트폴리오가 가장 잘 맞는 영역도 퍼블리싱입니다.

먼저 이 직무에서 실무 역량을 제대로 쌓고, 이후 업무상 필요한 범위에서 프론트엔드 역량을 확장하는 것이 순서라고 생각합니다.

Q10. 본인의 가장 큰 강점은 무엇입니까?

결과물을 완료했다는 보고보다 실제 결과를 확인하는 습관입니다.

HOOT UP에서도 AI가 완료했다고 보고한 작업과 실제 파일 수가 다른 경우가 있었고, 이후 배치 작업 후에는 반드시 예상 수량과 실제 결과를 비교하는 절차를 만들었습니다.

이전 상품기획과 생산 QA에서도 늘 샘플과 실제 양산품을 비교해왔기 때문에, “끝났다”보다 “정말 기준을 충족했는가”를 확인하는 방식이 제 강점이라고 생각합니다.

Q11. 본인의 단점은 무엇입니까?

문제를 발견하면 원인까지 충분히 이해하려는 성향이 있어서 작업 범위를 필요 이상으로 넓히는 경우가 있었습니다.

그래서 최근에는 작업 전에 목표와 완료 조건을 먼저 정하고, 지금 해결해야 할 문제와 이후 개선할 문제를 분리하려고 합니다. JW에서도 반응형 전체 커버리지를 먼저 완성하고 CSS 중복 제거는 별도의 리팩터링 단계로 분리했습니다.

Q12. 갈등이 생기면 어떻게 해결합니까?

사람을 기준으로 판단하기보다 요구사항과 결과물을 기준으로 이야기하려고 합니다.

예를 들어 디자인과 개발 의견이 다르면 각자의 취향보다 사용성, 접근성, 일정, 구현 비용, 유지보수성 같은 객관적 기준을 먼저 확인하고 대안을 찾겠습니다.

Q13. 피드백을 받으면 어떻게 합니까?

먼저 왜 그런 피드백이 나왔는지 확인합니다. 바로 동의하지 않더라도 요구사항과 목적에 맞는지 판단하고 타당하면 수정합니다.

중요한 것은 누가 말했느냐보다 근거가 맞는지라고 생각합니다.

Q14. 모르는 질문을 받으면 어떻게 합니까?

정확히 모르는 부분은 아는 범위까지 설명하고 확인이 필요하다고 말씀드리겠습니다. 잘못된 정보를 확신해서 말하는 것보다 정확하게 확인하는 게 낫다고 생각합니다.

예를 들어 API(응용프로그램 인터페이스) 이름이 정확히 기억나지 않더라도 문제를 어떤 순서로 확인할지는 설명할 수 있도록 준비하고 있습니다.

Q15. 반복적인 유지보수 업무도 괜찮습니까?

괜찮습니다. 퍼블리싱은 신규 제작뿐 아니라 기존 페이지 수정, 콘텐츠 교체, 크로스브라우징 확인, 접근성 보완 같은 반복 업무가 많다고 알고 있습니다.

오히려 반복 작업에서 공통 규칙을 정리하고 오류를 줄이는 것이 제가 가진 강점과 잘 맞는다고 생각합니다.

Q16. 포트폴리오 프로젝트와 실무는 다를 텐데요?

맞습니다. 개인 프로젝트는 제가 전체 의사결정을 했지만 실무에서는 기획자, 디자이너, 개발자와 협업해야 합니다.

그래서 개인 프로젝트 경험을 실무 경력과 동일하게 생각하지 않습니다. 다만 화면 구현과 문제 해결, 리팩터링, 검수 과정을 충분히 연습했다는 점에서 의미가 있다고 생각합니다.

Q17. 가장 실패했던 경험은 무엇입니까?

JW CSS 리팩터링 중 자동으로 만든 병합 목록에 누락이 있어 선택자 40개가 한 번에 빠진 적이 있습니다.

작업 전후 유효 스타일과 선택자를 대조하는 과정에서 당일 발견해 복구했고, 그 이후 선택자 개수 검산 자체를 완료 조건에 추가했습니다.

이 경험을 통해 도구가 만든 분석 결과도 그대로 믿지 않고 검증해야 한다는 기준을 만들었습니다.

Q18. 5년 후 어떤 모습이고 싶습니까?

퍼블리싱 실무를 안정적으로 담당하면서 HTML/CSS뿐 아니라 JavaScript 기반 인터랙션도 직접 처리할 수 있는 UI(사용자 인터페이스) 개발자에 가까운 웹퍼블리셔가 되고 싶습니다.

Q19. 왜 우리 회사에 지원했습니까?

공고에 맞춰 답을 바꿔야 합니다.

기본 구조는 다음과 같습니다.

공고에서 반응형 구축 / 웹표준·접근성 / 디자인 협업 / JavaScript UI(사용자 인터페이스) 구현을 중요하게 보고 있었고, 제가 프로젝트에서 실제로 집중했던 부분과 맞는다고 판단했습니다. 특히 ○○업무는 제가 기존 커머스·디자인 경험까지 같이 활용할 수 있다고 생각해 지원했습니다.

공고 문장 하나를 반드시 직접 언급하는 것이 좋습니다.

Q20. 웹퍼블리셔인데 디자인 포트폴리오를 왜 따로 만들었습니까?

웹퍼블리셔 채용공고 중에는 퍼블리싱뿐 아니라 디자인 역량도 함께 보는 회사가 있기 때문에 별도의 디자인 포트폴리오를 만들었습니다.

모든 회사에 웹디자이너로 지원하기 위한 자료라기보다, 필요할 경우 디자인 의도를 이해하고 직접 화면 설계까지 할 수 있다는 것을 보여주는 보조 포트폴리오입니다.

PART 2HTML·시맨틱 마크업

Q21. HTML은 무엇이고 어떤 역할을 합니까?

HTML은 웹페이지의 구조와 의미를 정의하는 마크업 언어입니다. CSS가 표현을 담당하고 JavaScript가 동작을 담당한다면 HTML은 페이지의 뼈대와 의미를 담당합니다.

예를 들어 제목은 heading, 주요 탐색은 nav, 핵심 콘텐츠는 main처럼 콘텐츠의 역할을 구조적으로 표현합니다.

Q22. HTML5의 주요 특징은 무엇입니까?

대표적으로 header, nav, main, section, article, footer 같은 시맨틱 요소가 추가됐고 오디오·비디오 같은 멀티미디어 요소, 다양한 form input type 등이 강화됐습니다.

Q23. 시맨틱 HTML이 무엇입니까?

태그의 이름 자체가 콘텐츠의 역할과 의미를 표현하도록 작성하는 방식입니다.

예를 들어 <div class="header"> 대신 <header>, 주요 탐색은 <nav>, 페이지 핵심 영역은 <main>을 사용할 수 있습니다.

시맨틱 태그를 많이 쓰는 것 자체가 목적은 아니며, 단순 레이아웃 wrapper라면 여전히 div가 자연스러울 수 있습니다.

Q24. div와 section은 언제 구분합니까?

div는 특별한 의미가 없는 범용 컨테이너이고, section은 하나의 주제나 의미를 가진 콘텐츠 구획입니다.

단순 스타일·레이아웃 wrapper라면 div가 자연스럽고, 제목을 포함하며 하나의 주제로 묶이는 콘텐츠라면 section을 고려합니다.

Q25. section과 article의 차이는 무엇입니까?

section은 문서 내부의 주제별 구획이고, article은 독립적으로 떼어내도 하나의 완전한 콘텐츠가 되는 영역입니다.

예를 들어 뉴스 페이지의 “인기 뉴스”는 section이 될 수 있고, 각 뉴스 기사 하나는 article이 될 수 있습니다.

Q26. a와 button은 어떻게 구분합니까?

사용자를 다른 URL이나 문서로 이동시키는 목적이면 <a>, 현재 페이지에서 상태를 변경하거나 기능을 실행하면 <button>을 사용합니다.

상품 상세 페이지로 이동하는 것은 a, 장바구니 패널을 여는 것·모달 닫기·탭 변경은 button이 적절합니다.

모양은 CSS로 만들 수 있으므로 시각 형태보다 기능의 의미를 기준으로 선택합니다.

Q27. strong과 b의 차이는 무엇입니까?

strong은 의미적 중요도를 표현하고, b는 의미적 중요도 없이 시각적으로 주의를 끄는 텍스트에 사용합니다.

Q28. em과 i의 차이는 무엇입니까?

em은 강조 의미를 갖고, i는 다른 어조·기술용어·외국어 표현 등 일반 본문과 구분되는 텍스트에 사용합니다.

Q29. label과 placeholder의 차이는 무엇입니까?

label은 입력 요소의 이름과 목적을 설명하는 요소이고, placeholder는 입력 예시나 힌트입니다.

placeholder는 사용자가 값을 입력하면 사라질 수 있기 때문에 label을 대체하면 안 됩니다.

HTML
<label for="email">이메일</label>
<input id="email" type="email" placeholder="name@example.com">

Q30. alt는 왜 필요합니까?

이미지를 직접 볼 수 없는 사용자에게 이미지가 전달하는 정보나 목적을 대체 텍스트로 제공하기 위해 사용합니다.

alt는 이미지의 생김새를 무조건 묘사하는 것이 아니라 현재 문맥에서 이미지가 전달하는 의미를 설명해야 합니다.

Q31. 모든 이미지에 설명형 alt가 필요합니까?

아닙니다. 의미를 전달하는 이미지에는 설명형 alt가 필요하지만 순수 장식 이미지는 alt=""로 처리해 스크린리더가 불필요하게 읽지 않도록 할 수 있습니다.

Q32. id와 class의 차이는 무엇입니까?

id는 문서 내 고유 식별자이고, class는 여러 요소에 재사용할 수 있습니다.

CSS 스타일링에서는 지나치게 강한 specificity를 피하기 위해 재사용 가능한 class 중심 구조를 선호하는 경우가 많습니다.

Q33. data-* 속성은 무엇입니까?

HTML 요소에 사용자 정의 데이터를 저장할 수 있는 표준 속성입니다.

HTML
<button data-target="panel1">탭</button>

JavaScript에서는 element(요소).dataset.target(실제 이벤트 발생 요소)처럼 접근할 수 있습니다.

Q34. defer와 async의 차이는 무엇입니까?

async는 다운로드가 끝나는 즉시 실행돼 script 간 순서가 보장되지 않을 수 있습니다.

defer는 HTML 파싱이 끝난 뒤 문서 순서대로 실행되므로 일반적인 애플리케이션 script에서 다루기 편한 경우가 많습니다.

Q35. meta viewport의 역할은 무엇입니까?

모바일 브라우저에서 layout(레이아웃) viewport와 초기 확대 비율을 제어합니다.

HTML
<meta name="viewport" content="width=device-width, initial-scale=1.0">

Q36. DOCTYPE은 왜 사용합니까?

브라우저에 HTML 문서 타입을 알려 standards mode로 렌더링되도록 합니다.

현대 HTML에서는 <!doctype html>을 사용합니다.

Q37. 페이지에 h1은 몇 개가 적절합니까?

HTML 자체가 여러 h1을 기술적으로 금지하는 것은 아니지만, 실무에서는 페이지 대표 제목을 하나 두는 구조가 명확하고 유지보수하기 쉽습니다.

heading은 글자 크기 때문에 고르는 것이 아니라 문서의 논리적 계층을 기준으로 정해야 합니다.

Q38. block과 inline(인라인) 요소의 차이는 무엇입니까?

전통적으로 block(블록) 요소는 새로운 줄에서 시작하고 가용 너비를 차지하며, inline(인라인) 요소는 텍스트 흐름 안에 배치됩니다.

다만 현대 CSS에서는 display 속성으로 표현 방식을 바꿀 수 있으므로 HTML 요소의 의미와 CSS 표현을 구분해서 이해하는 것이 좋습니다.

Q39. header와 head의 차이는 무엇입니까?

<head>는 title, meta, link(링크), script 같은 문서 메타데이터를 담는 영역입니다.

<header>는 body 안에서 로고, 제목, 내비게이션 등 페이지나 섹션의 머리말 콘텐츠를 담는 시맨틱 요소입니다.

Q40. main은 어떤 요소입니까?

해당 페이지의 핵심 콘텐츠를 나타내는 시맨틱 요소입니다.

반복되는 header, nav, footer 같은 영역과 구분해 주요 콘텐츠를 main으로 묶으면 문서 구조와 접근성이 명확해집니다.

PART 3CSS·레이아웃·반응형

Q41. CSS Cascade란 무엇입니까?

같은 요소의 같은 속성에 여러 CSS 선언이 적용될 때 최종적으로 어떤 선언이 사용될지 결정하는 전체 과정입니다.

단순히 specificity만 보는 것이 아니라 origin(스타일 출처), importance(중요도), cascade(계단식 우선순위) layer(계단식 레이어), specificity(명시도), source order(소스 작성 순서) 등이 함께 작동합니다.

따라서 “specificity가 가장 높은 rule이 항상 이긴다”라고만 설명하면 부족합니다.

Q42. Specificity란 무엇입니까?

여러 선택자가 같은 요소를 대상으로 할 때 선택자의 구체성 정도를 비교하는 기준입니다.

대략적으로 ID가 class보다 높고, class·attribute(속성)·pseudo-class가 element(요소)·pseudo-element보다 높습니다.

실무에서는 specificity를 계속 높여 충돌을 덮기보다 선택자 구조를 단순하게 유지하고 cascade를 예측 가능하게 만드는 것이 중요합니다.

Q43. :is()는 무엇입니까?

여러 선택자를 하나의 그룹으로 묶어 중복을 줄일 수 있는 pseudo-class입니다.

CSS
:is(.login, .register, .password).active {
  display: block;
}

다만 :is()의 specificity는 인수 목록 중 가장 높은 specificity를 가진 선택자를 따르기 때문에 병합 전후 cascade(계단식 우선순위) 관계가 변하지 않는지 확인해야 합니다.

Q44. :where()와 :is()의 차이는 무엇입니까?

둘 다 선택자 그룹화에 사용할 수 있지만 :where()의 specificity는 항상 0입니다.

그래서 쉽게 override되어야 하는 기본 스타일이나 reset(이력 위치 되돌리기) 계층에 유용할 수 있습니다.

Q45. !important를 왜 남발하면 안 됩니까?

일반적인 cascade(계단식 우선순위) 흐름을 강하게 덮기 때문에 이후 수정에서 더 강한 override가 필요해지고 유지보수가 어려워질 수 있습니다.

다만 !important 자체가 무조건 잘못된 것은 아니며, 사용자 preference나 특정 utility 등 명확한 이유가 있는 예외 상황에서는 사용할 수 있습니다.

핵심은 의도와 범위를 관리하는 것입니다.

Q46. Box Model을 설명해 주세요.

CSS 박스는 content(콘텐츠), padding(안쪽 여백), border(테두리), margin으로 구성됩니다.

기본 content-box에서는 width가 content(콘텐츠) 영역만 의미해 padding과 border가 추가되지만, border-box에서는 지정한 width 안에 padding과 border가 포함됩니다.

그래서 레이아웃 계산을 단순하게 하기 위해 전역으로 box-sizing: border-box를 적용하는 경우가 많습니다.

Q47. margin과 padding의 차이는 무엇입니까?

padding은 콘텐츠와 border(테두리) 사이의 내부 여백이고, margin은 요소 바깥쪽 요소와의 간격입니다.

배경은 일반적으로 padding(안쪽 여백) 영역까지 적용되지만 margin(바깥 여백) 영역에는 적용되지 않습니다.

Q48. Margin Collapse란 무엇입니까?

block(블록) 요소의 수직 margin이 특정 조건에서 서로 더해지지 않고 하나로 합쳐지는 현상입니다.

인접 block이나 부모와 첫 자식 사이 등에서 발생할 수 있습니다.

해결은 상황에 따라 padding(안쪽 여백), border(테두리), flex/grid formatting context, display: flow-root 등을 고려할 수 있습니다.

Q49. Flexbox를 설명해 주세요.

한 축을 중심으로 자식 요소를 배치하는 레이아웃 시스템입니다.

flex-direction이 main axis를 결정하고, justify-content는 main axis(주축), align-items는 cross axis(교차축) 정렬을 담당합니다.

“justify는 가로, align은 세로”라고만 외우면 flex-direction: column에서 틀리게 됩니다.

Q50. justify-content와 align-items의 차이는 무엇입니까?

justify-content는 main axis(주축) 방향의 배치와 남는 공간 분배를 담당하고, align-items는 cross axis(교차축) 방향의 item(항목) 정렬을 담당합니다.

Q51. flex-grow는 무엇입니까?

flex container에 남는 공간이 있을 때 item이 그 공간을 어떤 비율로 가져갈지 결정합니다.

예를 들어 grow 1과 grow 2인 두 item은 남는 공간을 1:2 비율로 나눠 갖습니다.

Q52. flex-shrink는 무엇입니까?

container(컨테이너) 공간이 부족할 때 flex item이 기본 크기보다 얼마나 줄어들지 결정하는 비율입니다.

flex item(항목) 안의 긴 텍스트가 줄어들지 않을 때 min-width: 0이 필요한 경우도 자주 있습니다.

Q53. flex-basis는 무엇입니까?

flex item의 main axis(주축) 방향 기본 크기를 결정합니다. grow와 shrink 계산 전의 기준 크기라고 이해하면 됩니다.

Q54. flex: 1은 어떤 의미입니까?

일반적으로 flex: 1 1 0%에 가까운 shorthand로 해석됩니다.

남는 공간을 균등하게 나누는 레이아웃에서 자주 사용합니다.

Q55. Grid와 Flex를 언제 구분해서 씁니까?

Flex는 한 축 중심 배치에 강하고 Grid는 행과 열을 동시에 정의하는 2차원 레이아웃에 강합니다.

헤더 내비게이션·버튼 그룹은 Flex가 자연스럽고 상품 카드 목록처럼 행과 열 구조가 중요한 영역은 Grid가 편리합니다.

둘 중 하나가 무조건 더 좋은 것이 아니라 콘텐츠 구조를 기준으로 선택합니다.

Q56. 1fr은 무엇입니까?

Grid에서 사용 가능한 남은 공간을 비율로 나눠 갖는 단위입니다.

1fr 2fr이면 남은 공간을 1:2 비율로 분배합니다.

Q57. minmax()는 무엇입니까?

Grid(그리드) track의 최소 크기와 최대 크기를 동시에 지정하는 함수입니다.

CSS
grid-template-columns: repeat(auto-fit, minmax(240px, 1fr));

처럼 최소 240px을 유지하면서 남는 공간을 확장할 수 있습니다.

Q58. auto-fit과 auto-fill의 차이는 무엇입니까?

둘 다 가능한 만큼 grid track을 반복하지만 빈 track(그리드 행·열 트랙) 처리 방식이 다릅니다.

auto-fill은 가능한 track(그리드 행·열 트랙) 자체를 유지하고, auto-fit은 빈 track을 접어 실제 item이 남는 공간을 사용할 수 있게 합니다.

Q59. position 속성 종류를 설명해 주세요.

static은 기본 흐름, relative는 원래 위치를 기준으로 이동하면서 positioned ancestor가 될 수 있고, absolute는 normal flow에서 빠져 containing block(배치 기준 영역) 기준으로 배치됩니다.

fixed는 일반적으로 viewport에 고정되고, sticky는 일반 흐름을 따르다가 지정된 지점에서 고정됩니다.

Q60. position absolute의 기준점은 무엇입니까?

가장 가까운 positioned ancestor의 containing block을 기준으로 합니다.

“무조건 부모”라고 답하면 정확하지 않습니다. 일반적으로 부모에 position: relative를 지정해 기준을 만드는 경우가 많습니다.

Q61. relative는 왜 사용합니까?

요소 자체를 상대 이동시키는 용도도 있지만, absolute 자식의 containing block을 만들기 위해 자주 사용합니다.

Q62. fixed와 sticky의 차이는 무엇입니까?

fixed는 일반적으로 normal flow에서 빠져 viewport에 고정되고, sticky는 원래 레이아웃 공간을 유지하면서 특정 scroll threshold 이후 고정됩니다.

Q63. sticky가 안 되는 대표 원인은 무엇입니까?

top 같은 inset 미지정, 부모의 overflow 설정, sticky가 움직일 공간 부족, scroll container(스크롤 컨테이너) 구조 문제 등을 먼저 확인합니다.

Q64. z-index가 안 먹는 이유는 무엇입니까?

단순 숫자 크기보다 stacking context가 중요합니다.

서로 다른 stacking context(쌓임 맥락) 안에 있으면 자식의 z-index가 매우 커도 다른 stacking context의 상위 요소를 넘지 못할 수 있습니다.

position+z-index, opacity<1, transform(변형), filter 등은 stacking context를 만들 수 있습니다.

Q65. display:none, visibility:hidden, opacity:0의 차이는 무엇입니까?

display:none은 레이아웃에서도 제거되고 일반적으로 accessibility(접근성) tree에서도 제외됩니다.

visibility:hidden은 공간은 유지하지만 보이지 않습니다.

opacity:0은 시각적으로 투명하지만 레이아웃에는 남고 이벤트를 받을 수 있습니다.

Q66. pseudo-class와 pseudo-element의 차이는 무엇입니까?

pseudo-class는 요소의 상태나 조건을 나타냅니다. 예: :hover(마우스 올림 상태), :focus(초점), :nth-child().

pseudo-element는 요소의 특정 부분이나 가상 요소를 나타냅니다. 예: ::before, ::after, ::first-line.

Q67. nth-child와 nth-of-type의 차이는 무엇입니까?

nth-child()는 전체 형제 중 위치를 기준으로 하고, nth-of-type()은 같은 태그 유형 중 위치를 기준으로 합니다.

Q68. em과 rem의 차이는 무엇입니까?

rem은 root(html)의 font-size를 기준으로 하고, em은 현재 요소의 계산된 font-size를 기준으로 합니다.

rem은 전체 typography scale(확대·축소) 관리에 편하고, em은 컴포넌트 내부 상대 크기 관리에 유용할 수 있습니다.

Q69. px를 쓰면 반응형이 아닌가요?

아닙니다. 반응형 여부는 px 사용 자체로 결정되지 않습니다.

border(테두리) 1px처럼 고정 단위가 자연스러운 경우가 있고, layout에서는 %, fr, rem, clamp 등 상대 단위와 혼합해 사용할 수 있습니다.

Q70. vw와 vh는 무엇입니까?

1vw는 viewport(화면 표시 영역) width의 1%, 1vh는 viewport(화면 표시 영역) height의 1%입니다.

모바일에서는 브라우저 UI(사용자 인터페이스) 때문에 전통적인 100vh가 실제 보이는 높이와 다를 수 있어 dvh, svh, lvh 같은 단위도 사용됩니다.

Q71. CSS Custom Property를 설명해 주세요.

--name 형태로 값을 정의하고 var(--name)으로 참조하는 CSS 변수 기능입니다.

runtime에 실제로 존재하고 cascade와 상속의 영향을 받기 때문에 테마·디자인 토큰·브레이크포인트별 값 재정의 등에 유용합니다.

Q72. CSS 변수와 Sass 변수의 차이는 무엇입니까?

CSS custom property는 브라우저 runtime에 남아 cascade와 상속을 활용할 수 있습니다.

Sass 변수는 preprocessing 단계에서 값으로 치환돼 최종 CSS에는 일반적으로 변수로 남지 않습니다.

Q73. Responsive(반응형) Web이 무엇입니까?

하나의 웹 콘텐츠가 viewport(화면 표시 영역) 크기와 사용 환경에 따라 레이아웃과 인터랙션 방식을 유동적으로 변경하는 구현 방식입니다.

단순히 크기를 줄이는 것이 아니라 필요하면 navigation 패턴이나 콘텐츠 우선순위 자체를 바꿀 수 있습니다.

Q74. 브레이크포인트는 어떤 기준으로 정합니까?

특정 기기 이름이나 관례적 숫자만 기준으로 하지 않고 콘텐츠가 정상적으로 유지되는 한계 지점을 기준으로 잡는 것이 좋습니다.

JW Anderson에서는 메가메뉴가 안정적으로 배치되는 최소 폭을 기준으로 1280px을 desktop(데스크톱) 시작점으로 잡았고, desktop(데스크톱) 내부에서도 상품 카드 밀도를 유지하기 위해 추가 구간을 나눴습니다.

Q75. Mobile First란 무엇입니까?

작은 화면을 기본 스타일로 작성한 뒤 min-width media query로 큰 화면을 확장하는 접근입니다.

핵심 콘텐츠 우선순위를 명확히 하고 기본 CSS를 단순화하는 데 도움이 될 수 있지만, 모든 프로젝트에 절대적인 정답은 아닙니다.

Q76. CSS가 안 먹을 때 어떤 순서로 디버깅합니까?

  1. selector가 실제 요소와 매칭되는지 확인
  2. CSS 파일이 로드됐는지 확인
  3. DevTools Styles panel에 rule이 존재하는지 확인
  4. 취소선이면 cascade(계단식 우선순위)/specificity(명시도)/source order(소스 작성 순서) 확인
  5. media query(미디어 쿼리) 조건 확인
  6. inline(인라인) style(인라인 스타일)/!important 확인
  7. shorthand가 덮었는지 확인
  8. 상속 여부 확인
  9. flex/grid/position/box model 같은 layout(레이아웃) context 확인

무작정 더 강한 selector나 !important를 추가하기보다 원인을 좁혀야 합니다.

Q77. 모바일에서 가로 스크롤이 생기면 어떻게 디버깅합니까?

overflow-x:hidden으로 바로 숨기지 않고 viewport(화면 표시 영역) 밖으로 나간 요소를 먼저 찾습니다.

100vw, width+padding(안쪽 여백), min-width, absolute, transform(변형), 긴 문자열, 이미지 intrinsic width(고유 너비), negative margin(음수 마진), pseudo-element(의사 요소) 등을 확인합니다.

DevTools에서 문제 요소의 bounding box와 computed width를 보는 것이 좋습니다.

Q78. Flex에서 text ellipsis가 안 되는 이유는 무엇일 수 있습니까?

flex item의 기본 minimum size 때문에 item이 충분히 줄어들지 못할 수 있습니다.

CSS
.info {
  flex: 1;
  min-width: 0;
}

ellipsis(말줄임) 자체에는 overflow:hidden, white-space:nowrap, text-overflow:ellipsis(말줄임)가 필요합니다.

Q79. hover(마우스 올림 상태) 확대에서 grid가 흔들리지 않게 하려면?

card 자체의 width를 바꾸지 않고 이미지에 transform(변형): scale()을 적용하고 wrapper에 overflow:hidden을 둡니다.

CSS
.thumb { overflow:hidden; }
.thumb img { transition: transform .3s; }
.card:hover img { transform: scale(1.1); }

Q80. CSS 중복을 리팩터링한다면 어떤 원칙을 쓰겠습니까?

여러 breakpoint에서 동일한 declaration은 base로 승격하고, 각 breakpoint에는 실제로 달라지는 값만 남깁니다.

이 방식은 JW Anderson CSS 리팩터링의 핵심이었습니다. 목표는 단순 줄 수 감소가 아니라 동일 컴포넌트의 변경 지점을 줄이는 것이었습니다.

PART 4JavaScript 심층 기술면접

Q81. JavaScript는 웹에서 어떤 역할을 합니까?

웹페이지에 동작과 상태 변화를 추가합니다. DOM(문서 객체 모델) 조작, 사용자 이벤트 처리, 데이터 통신, 상태 변경 등을 담당합니다.

웹퍼블리싱에서는 메뉴, 탭, 아코디언, 모달, 슬라이드, 폼 검증 같은 UI(사용자 인터페이스) 인터랙션 구현에 많이 사용합니다.

Q82. JavaScript는 어떤 타입 시스템을 가집니까?

동적 타입 언어입니다. 변수에 고정 타입을 선언하는 것이 아니라 실행 중 값에 따라 타입이 결정됩니다.

JS
let value = 10;
value = 'hello';

Q83. var, let, const의 차이는 무엇입니까?

var는 함수 스코프이고 let, const는 블록 스코프입니다.

var는 같은 스코프에서 재선언·재할당 가능, let은 재할당 가능하지만 재선언 불가, const는 재할당할 수 없습니다.

실무에서는 변경하지 않을 binding은 const, 변경이 필요한 경우 let을 기본으로 사용합니다.

Q84. const 객체 내부 값은 변경 가능한가요?

가능합니다.

JS
const user = { name: 'Kim' };
user.name = 'Lee';

const는 객체를 immutable하게 만드는 것이 아니라 변수 binding의 재할당을 막습니다.

Q85. Scope란 무엇입니까?

변수나 함수에 접근할 수 있는 범위입니다.

대표적으로 global scope(유효 범위), function scope(유효 범위), block(블록) scope가 있습니다. let과 const는 block(블록) scope를 따릅니다.

Q86. Lexical Scope란 무엇입니까?

함수가 어디에서 호출됐는지가 아니라 어디에서 정의됐는지를 기준으로 상위 스코프가 결정되는 방식입니다.

Q87. Hoisting이란 무엇입니까?

실행 전에 선언 정보가 처리돼 선언이 위로 올라간 것처럼 보이는 현상입니다.

var는 선언 후 초기값 undefined처럼 보일 수 있고, let/const도 선언은 hoist되지만 초기화 전 TDZ(일시적 사각지대) 때문에 접근할 수 없습니다.

Q88. TDZ란 무엇입니까?

Temporal Dead Zone의 약자로, let/const가 선언된 스코프에 진입한 시점부터 실제 선언문에 도달하기 전까지 해당 변수에 접근할 수 없는 구간입니다.

Q89. Primitive Type에는 무엇이 있습니까?

string, number, bigint, boolean, undefined, symbol, null 등이 있습니다.

typeof null이 "object"를 반환하는 것은 JavaScript의 오래된 특이점입니다.

Q90. Primitive와 Object의 차이는 무엇입니까?

primitive는 값 자체가 복사되지만 객체는 같은 객체 reference를 공유할 수 있습니다.

JS
const a = { value: 10 };
const b = a;
b.value = 20;

이 경우 a.value도 20이 됩니다.

Q91. 얕은 복사와 깊은 복사의 차이는?

spread syntax로 객체를 복사하면 기본적으로 shallow copy입니다.

중첩 객체의 reference는 공유될 수 있습니다. 깊은 복사가 필요하고 데이터 타입이 지원된다면 structuredClone() 같은 방법을 사용할 수 있습니다.

Q92. null과 undefined의 차이는?

undefined는 값이 아직 지정되지 않았거나 존재하지 않을 때 자연스럽게 발생하는 경우가 많고, null은 개발자가 의도적으로 “값이 없음”을 표현할 때 자주 사용합니다.

Q93. ==와 ===의 차이는?

==는 비교 과정에서 type coercion이 발생할 수 있고, ===는 타입과 값이 모두 같아야 true입니다.

예측하지 못한 암묵적 형변환을 줄이기 위해 일반적으로 ===를 사용합니다.

Q94. Truthy와 Falsy를 설명해 주세요.

대표 falsy(거짓으로 평가되는 값) 값은 false, 0, -0, 0n, "", null, undefined, NaN입니다.

반대로 [], {}, '0', 'false' 같은 값은 truthy입니다.

Q95. NaN이 무엇입니까?

Not-a-Number를 의미하지만 타입은 number입니다.

JS
Number('hello'); // NaN
typeof NaN;      // 'number'

검사는 Number.isNaN(value)를 사용하는 것이 좋습니다.

Q96. 함수 선언식과 함수 표현식의 차이는?

함수 선언식은 선언 단계에서 함수 전체가 처리돼 선언 이전 호출이 가능할 수 있지만, 함수 표현식은 변수 초기화 이후에 사용할 수 있습니다.

JS
function add(a,b){ return a+b; }
const add2 = function(a,b){ return a+b; };

Q97. Arrow Function은 무엇입니까?

함수 표현을 간결하게 작성할 수 있는 문법입니다.

가장 중요한 차이 중 하나는 arrow function이 자체 this를 만들지 않고 lexical scope의 this를 사용한다는 점입니다.

Q98. this는 무엇입니까?

일반 함수에서는 함수가 어떻게 호출됐는지에 따라 참조 대상이 결정될 수 있는 특별한 값입니다.

객체 method에서 user.hello()처럼 호출하면 this가 user를 가리킬 수 있습니다.

arrow function은 자체 this를 만들지 않습니다.

Q99. jQuery 이벤트에서 arrow function을 왜 조심해야 합니까?

jQuery 이벤트 callback에서 $(this)를 클릭 요소로 사용할 때 일반 function을 써야 의도한 요소를 가리키는 경우가 많습니다.

JS
$('.btn').on('click', function () {
  $(this).addClass('active');
});

arrow function에서는 자체 this가 없으므로 $(this)가 클릭 요소를 뜻하지 않을 수 있습니다.

Q100. Closure란 무엇입니까?

함수가 생성될 당시의 lexical scope를 기억해 외부 함수 실행이 끝난 뒤에도 그 변수에 접근할 수 있는 특성입니다.

JS
function counter(){
  let count = 0;
  return function(){
    count++;
    return count;
  };
}

Q101. Callback Function이란 무엇입니까?

다른 함수에 인수로 전달되어 특정 시점에 실행되는 함수입니다.

이벤트 핸들러, 배열 메서드, 비동기 처리에서 자주 사용합니다.

Q102. 배열과 객체의 차이는 무엇입니까?

배열은 순서가 있는 값의 collection이고, 객체는 key-value 형태의 property(속성) 집합입니다.

배열도 JavaScript에서 Object의 한 종류이지만 데이터 의미에 따라 적절히 선택합니다.

Q103. forEach()는 무엇입니까?

배열의 각 요소에 callback을 실행합니다. 새 배열을 만드는 것이 목적은 아닙니다.

JS
products.forEach(product => console.log(product));

Q104. map()은 무엇입니까?

각 요소를 변환해 동일한 길이의 새 배열을 반환합니다.

JS
const prices = products.map(p => p.price);

Q105. map과 forEach의 차이는?

map은 callback(콜백 함수) 결과를 모아 새 배열을 반환하는 데이터 변환에 적합하고, forEach는 각 요소에 side effect(부수 효과) 작업을 수행할 때 사용합니다.

Q106. filter()는 무엇입니까?

조건을 만족하는 요소만 모아 새 배열을 반환합니다.

JS
const expensive = products.filter(p => p.price >= 100000);

Q107. find()는 무엇입니까?

조건에 맞는 첫 번째 요소 하나를 반환하고 없으면 undefined를 반환합니다.

filter가 배열을 반환하는 것과 다릅니다.

Q108. some()과 every()의 차이는?

some()은 하나라도 조건을 만족하면 true, every()는 모든 요소가 조건을 만족해야 true입니다.

Q109. reduce()는 무엇입니까?

배열을 순회하면서 하나의 누적 결과를 만들 때 사용합니다.

JS
const total = cart.reduce(
  (sum, item) => sum + item.price * item.quantity,
  0
);

Q110. slice()와 splice()의 차이는?

slice()는 원본을 변경하지 않고 일부를 복사한 새 배열을 반환합니다.

splice()는 원본 배열을 직접 변경해 요소를 삭제하거나 추가합니다.

Q111. Spread Syntax는 무엇입니까?

배열이나 객체를 펼쳐 새 배열·객체를 만들 때 사용합니다.

JS
const next = [...previous, newItem];
const nextUser = { ...user, name: 'Shin' };

기본적으로 shallow copy입니다.

Q112. Rest Parameter는 무엇입니까?

여러 argument를 하나의 배열로 모을 때 사용합니다.

JS
function sum(...numbers) { ... }

Q113. Destructuring은 무엇입니까?

객체나 배열 값을 변수로 쉽게 분해하는 문법입니다.

JS
const { name, price } = product;
const [first, second] = items;

Q114. Optional Chaining은 무엇입니까?

중간 값이 null/undefined여도 오류 없이 undefined를 반환하도록 안전하게 property에 접근할 수 있습니다.

JS
user?.profile?.name

Q115. Nullish Coalescing(널 병합 연산자) ??는 무엇입니까?

왼쪽 값이 null 또는 undefined일 때만 fallback 값을 사용합니다.

JS
const name = user.name ?? 'Guest';

||와 달리 0, false, 빈 문자열을 유효값으로 유지합니다.

Q116. DOM이 무엇입니까?

브라우저가 HTML 문서를 JavaScript에서 다룰 수 있도록 객체 트리 형태로 표현한 모델입니다.

JavaScript는 DOM(문서 객체 모델) API를 통해 요소를 선택하고 text, attribute(속성), class, style 등을 변경할 수 있습니다.

Q117. HTML과 DOM은 같은 것입니까?

아닙니다. HTML은 문서 소스이고, DOM은 브라우저가 HTML을 파싱해 만든 객체 모델입니다.

JavaScript가 DOM을 변경해도 원본 HTML 파일 자체가 변경되는 것은 아닙니다.

Q118. querySelector와 querySelectorAll의 차이는?

querySelector()는 첫 번째 일치 요소를 반환하고, querySelectorAll()은 모든 일치 요소를 static NodeList로 반환합니다.

Q119. NodeList와 Array는 같은가요?

아닙니다. NodeList는 array-like collection이지만 Array와 동일하지 않습니다.

JS
const items = [...document.querySelectorAll('.item')];

처럼 배열로 변환할 수 있습니다.

Q120. classList는 무엇입니까?

DOM(문서 객체 모델) 요소의 class를 조작하는 API입니다.

JS
element.classList.add('active');
element.classList.remove('active');
element.classList.toggle('active');
element.classList.contains('active');

Q121. innerHTML과 textContent의 차이는?

innerHTML은 문자열을 HTML markup으로 파싱하지만 textContent는 plain text로 처리합니다.

사용자 입력을 innerHTML로 그대로 삽입하면 XSS(교차 사이트 스크립팅) 위험이 있으므로 단순 텍스트는 textContent가 안전합니다.

Q122. Event란 무엇입니까?

브라우저에서 발생하는 사용자 또는 시스템 동작입니다. click, input, change, submit, keydown, scroll, load 등이 있습니다.

JavaScript에서는 addEventListener로 반응할 수 있습니다.

Q123. Event(이벤트) Bubbling이 무엇입니까?

target(실제 이벤트 발생 요소) 요소에서 발생한 이벤트가 DOM(문서 객체 모델) 트리의 부모 방향으로 전파되는 과정입니다.

Q124. Event(이벤트) Capturing이 무엇입니까?

이벤트가 상위 document 영역에서 target(실제 이벤트 발생 요소) 방향으로 내려오는 단계입니다.

전체 흐름은 capturing → target(실제 이벤트 발생 요소) → bubbling입니다.

Q125. event.target과 event.currentTarget의 차이는?

target(실제 이벤트 발생 요소)은 실제 이벤트가 시작된 요소이고, currentTarget(현재 이벤트 처리 요소)은 현재 listener가 등록돼 실행되고 있는 요소입니다.

button 안 span을 클릭했다면 target은 span, currentTarget은 button일 수 있습니다.

Q126. Event(이벤트) Delegation이 무엇입니까?

여러 자식 요소 각각에 listener를 등록하지 않고 공통 부모 하나에 listener를 등록해 bubbling을 이용하는 방식입니다.

동적으로 추가되는 요소도 처리하기 좋습니다.

JS
list.addEventListener('click', e => {
  const item = e.target.closest('.item');
  if (!item) return;
});

Q127. preventDefault와 stopPropagation의 차이는?

preventDefault()는 브라우저의 기본 동작을 막고, stopPropagation()은 이벤트 전파를 막습니다.

둘은 전혀 다른 역할입니다.

Q128. DOMContentLoaded와 load의 차이는?

DOMContentLoaded는 HTML 파싱이 끝나 DOM이 준비됐을 때 발생하고, load는 이미지 등 종속 리소스까지 모두 로드된 뒤 발생합니다.

Q129. 동기와 비동기의 차이는?

동기는 앞 작업이 끝나야 다음 작업이 진행되고, 비동기는 오래 걸리는 작업의 완료를 기다리는 동안 다른 작업을 수행할 수 있게 합니다.

네트워크 요청이 대표적인 비동기 작업입니다.

Q130. Call Stack이 무엇입니까?

현재 실행 중인 함수 호출을 stack 구조로 관리합니다. 함수가 호출되면 stack에 쌓이고 실행이 끝나면 빠집니다.

Q131. Event(이벤트) Loop를 간단히 설명해 주세요.

JavaScript는 call stack에서 한 번에 하나의 작업을 실행합니다.

비동기 callback이나 Promise(비동기 결과 객체) 결과는 queue에 대기하고, event loop가 call stack이 비었을 때 실행 가능한 작업을 넘겨줍니다.

Q132. Promise란 무엇입니까?

비동기 작업의 미래 성공 또는 실패 결과를 표현하는 객체입니다.

상태는 pending(대기), fulfilled(이행·성공), rejected가 있습니다.

Q133. async/await는 무엇입니까?

Promise(비동기 결과 객체) 기반 비동기 코드를 순차적으로 읽히는 형태로 작성할 수 있게 하는 문법입니다.

async 함수는 Promise를 반환하고, await는 해당 async 함수의 흐름을 일시 중지합니다.

Q134. fetch에서 404면 자동으로 catch로 갑니까?

반드시 그렇지 않습니다. HTTP 404/500이어도 Response(응답 객체) 객체를 받을 수 있으므로 response.ok를 직접 확인하는 것이 안전합니다.

JS
const response = await fetch(url);
if (!response.ok) throw new Error(`HTTP ${response.status}`);

Q135. JSON이 무엇입니까?

문자열 기반 데이터 교환 형식입니다.

JS 값을 JSON(자바스크립트 객체 표기법 기반 데이터 형식) 문자열로 만들 때 JSON(자바스크립트 객체 표기법 기반 데이터 형식).stringify(), JSON(자바스크립트 객체 표기법 기반 데이터 형식) 문자열을 JS 값으로 바꿀 때 JSON(자바스크립트 객체 표기법 기반 데이터 형식).parse()를 사용합니다.

Q136. localStorage란 무엇입니까?

브라우저에 origin별 key-value 형태로 데이터를 저장하는 Web Storage API입니다. 문자열 기반이며 일반적으로 브라우저를 닫아도 유지됩니다.

민감정보 저장에는 적합하지 않습니다.

Q137. 객체를 localStorage에 저장하려면?

문자열 기반이므로 JSON으로 변환해 저장합니다.

JS
localStorage.setItem('cart', JSON.stringify(cart));
const cart = JSON.parse(localStorage.getItem('cart')) ?? [];

Q138. localStorage와 sessionStorage의 차이는?

localStorage는 명시적으로 제거하기 전까지 일반적으로 유지되고, sessionStorage는 해당 탭/세션 단위로 유지됩니다.

Q139. Cookie와 localStorage의 차이는?

Cookie는 HTTP 요청에 자동 포함될 수 있고 서버와 연동되는 성격이 있으며 용량이 작습니다.

localStorage는 클라이언트 측 저장소이고 요청에 자동 포함되지 않습니다.

Q140. Debounce란 무엇입니까?

연속 호출이 멈춘 뒤 일정 시간이 지나면 한 번 실행하는 패턴입니다.

검색 input처럼 사용자가 계속 타이핑하는 동안 API(응용프로그램 인터페이스) 요청이 반복되는 것을 줄이는 데 유용합니다.

Q141. Throttle이란 무엇입니까?

연속 이벤트에서 일정 시간당 최대 실행 횟수를 제한하는 패턴입니다.

scroll, resize 같은 고빈도 이벤트에 유용합니다.

Debounce는 “멈춘 뒤 실행”, Throttle은 “일정 주기 실행”으로 구분하면 됩니다.

Q142. setTimeout은 정확히 지정한 시간 후 실행됩니까?

꼭 그렇지는 않습니다. 지정 시간 이후 실행 가능한 최소 시점을 의미하고, call stack이 바쁘면 더 늦게 실행될 수 있습니다.

Q143. Form Validation은 frontend만 하면 됩니까?

아닙니다. frontend(프론트엔드) validation은 사용자 경험을 위해 필요하지만 실제 보안과 데이터 무결성은 server-side(서버 측) validation이 반드시 필요합니다.

Q144. JS에서 style 직접 변경과 class 변경 중 어떤 게 좋습니까?

단순 UI(사용자 인터페이스) state라면 JavaScript에서는 class나 attribute만 변경하고 실제 표현은 CSS에 두는 방식을 선호합니다.

JS는 상태, CSS는 표현을 담당하게 하면 유지보수성이 좋습니다.

Q145. Modal을 구현할 때 무엇을 고려합니까?

기능적으로 open/close, overlay, Escape 등을 고려하고, 접근성 측면에서는 dialog(대화상자) semantics, accessible name(접근 가능한 이름), focus(초점) 이동, focus(초점) trap(초점 가두기), 닫은 후 trigger로 focus(초점) 복귀, background interaction(상호작용) 제어 등을 고려합니다.

Q146. Accordion(접고 펼치는 UI(사용자 인터페이스)) 구현에서 중요한 것은?

시각 상태와 접근성 상태를 같이 동기화하는 것입니다.

HTML
<button aria-expanded="false" aria-controls="panel1">...</button>
<div id="panel1" hidden>...</div>

JS에서 열림 상태에 따라 aria-expanded와 hidden을 함께 갱신합니다.

Q147. Tab UI를 구현할 때 무엇을 고려합니까?

기본적으로 active tab과 target(실제 이벤트 발생 요소) panel을 연결해야 하고, 접근성까지 고려하면 role=tablist, role=tab, role=tabpanel, aria-selected, 방향키 navigation, focus(초점) 관리 등을 고려합니다.

Q148. 동적으로 추가한 요소에 이벤트가 안 붙는 이유는?

처음 querySelectorAll()로 잡은 요소에만 listener가 등록됐기 때문일 수 있습니다.

공통 부모에 event delegation을 적용하면 이후 생성된 자식도 처리할 수 있습니다.

Q149. Cannot read properties(속성) of null이 나오면 무엇을 봅니까?

selector(선택자) 오타, 해당 페이지에 요소가 없는지, DOM이 생성되기 전에 script가 실행됐는지 확인합니다.

무조건 if(element(요소))로 에러만 숨기기보다 왜 null인지 원인을 먼저 봅니다.

Q150. 이벤트가 두 번 실행되면 무엇을 확인합니까?

listener(이벤트 감지 함수) 중복 등록, script 중복 로드, 초기화 함수 중복 호출, 부모와 자식의 bubbling, 여러 handler가 동시에 등록됐는지 확인합니다.

바로 stopPropagation()으로 막기보다 원인을 찾습니다.

Q151. XSS가 무엇입니까?

신뢰할 수 없는 사용자 입력 등을 HTML/JS context에 안전하지 않게 삽입해 script가 실행될 수 있는 보안 취약점입니다.

plain text라면 innerHTML보다 textContent를 사용하고, 외부 입력을 그대로 HTML로 삽입하지 않는 것이 중요합니다.

Q152. setTimeout과 Promise가 함께 있을 때 실행 순서는?

현재 call stack이 끝난 뒤 Promise(비동기 결과 객체) callback은 microtask queue에서 먼저 처리되고, setTimeout callback은 task/macrotask queue에서 처리됩니다.

JS
console.log(1);
setTimeout(() => console.log(2), 0);
Promise.resolve().then(() => console.log(3));
console.log(4);

출력은 1, 4, 3, 2입니다.

PART 5jQuery

Q153. jQuery는 무엇입니까?

DOM(문서 객체 모델) 탐색·조작, 이벤트, animation(애니메이션) 등을 간결한 API로 제공하는 JavaScript library입니다.

신규 개발에서는 Vanilla JS나 framework(프레임워크) 비중이 커졌지만, 웹에이전시·기존 사이트 유지보수에서는 jQuery 기반 코드가 여전히 존재하기 때문에 웹퍼블리셔에게 실무적으로 의미가 있습니다.

Q154. $()는 무엇입니까?

jQuery 함수입니다. CSS selector로 요소를 찾거나 DOM(문서 객체 모델) 요소를 jQuery 객체로 감쌀 수 있습니다.

JS
$('.menu')
$(this)

Q155. jQuery 객체와 DOM(문서 객체 모델) 객체는 같은가요?

아닙니다.

DOM(문서 객체 모델) 객체는 classList.add(), jQuery 객체는 .addClass() 같은 서로 다른 API를 사용합니다.

Q156. .on()은 무엇입니까?

이벤트를 등록하는 jQuery 메서드입니다.

JS
$('.btn').on('click', function(){ ... });

직접 이벤트뿐 아니라 delegation 형태로도 사용할 수 있습니다.

Q157. .click()과 .on('click')의 차이는?

둘 다 클릭 handler를 등록할 수 있지만 .on()은 다양한 이벤트를 일관되게 처리하고 event delegation도 지원하므로 더 유연합니다.

Q158. jQuery Event(이벤트) Delegation(이벤트 위임) 코드를 작성해 보세요.

JS
$('.list').on('click', '.item', function () {
  $(this).toggleClass('active');
});

부모에 listener를 두고 bubbling을 이용하므로 동적으로 추가된 .item(항목)에도 대응할 수 있습니다.

Q159. .attr()과 .prop()의 차이는?

.attr()은 HTML attribute(속성) 값을 다루고, .prop()은 DOM(문서 객체 모델) property의 현재 상태를 다룹니다.

checkbox의 현재 checked 상태는 .prop('checked')가 적절합니다.

Q160. .find()와 .children()의 차이는?

.children()은 직접 자식만 찾고, .find()는 모든 후손 중 조건과 일치하는 요소를 찾습니다.

Q161. .parent()와 .parents()의 차이는?

.parent()는 직접 부모 하나를, .parents()는 모든 조상 중 조건에 맞는 요소들을 찾습니다.

Q162. .closest()는 무엇입니까?

현재 요소부터 시작해 위쪽 조상 방향으로 올라가며 최초로 일치하는 요소를 찾습니다.

UI(사용자 인터페이스) 이벤트에서 클릭한 버튼이 속한 카드 같은 상위 컴포넌트를 찾는 데 자주 사용합니다.

Q163. .eq()는 무엇입니까?

jQuery collection에서 특정 index 요소를 선택합니다.

JS
$('.tab').eq(2)

Q164. .each()는 무엇입니까?

jQuery collection을 순회합니다.

JS
$('.item').each(function(index){
  console.log(index, $(this).text());
});

Q165. jQuery animation을 무조건 써야 합니까?

아닙니다. 단순 state(상태) animation은 CSS transition(전환 효과)/animation이 더 적합한 경우가 많습니다.

JS/jQuery는 상태 변경, CSS는 표현을 담당하는 구조가 유지보수에 유리할 수 있습니다.

Q166. jQuery this와 arrow function의 관계는?

jQuery callback에서 $(this)를 클릭 요소로 사용하려면 일반 function을 쓰는 패턴이 많습니다.

arrow function은 자체 this를 만들지 않기 때문에 의도한 element가 아닐 수 있습니다.

Q167. jQuery가 있는데 Vanilla JS를 왜 알아야 합니까?

jQuery API만 외우는 것보다 DOM과 event가 실제 JavaScript에서 어떻게 동작하는지를 알아야 jQuery 코드도 이해할 수 있고 새로운 프로젝트나 다른 framework에도 적응할 수 있기 때문입니다.

PART 6접근성·웹표준·크로스브라우징·성능·SEO(검색엔진 최적화)·Git

Q168. 웹접근성이란 무엇입니까?

장애 여부나 사용 환경과 관계없이 가능한 많은 사용자가 웹 콘텐츠와 기능을 이용할 수 있도록 만드는 것입니다.

퍼블리셔 관점에서는 시맨틱 HTML, 대체 텍스트, 키보드 접근, focus(초점) 표시, form label, heading 구조, ARIA(접근성 보조 속성 체계) 상태 관리 등을 고려합니다.

Q169. WCAG가 무엇입니까?

Web Content Accessibility(접근성) Guidelines의 약자로 웹 접근성 국제 가이드라인입니다.

핵심 원칙은 POUR입니다.

  • Perceivable(인지 가능): 인지 가능
  • Operable(조작 가능): 조작 가능
  • Understandable(이해 가능): 이해 가능
  • Robust(견고성): 보조기술·브라우저와의 견고한 호환

Q170. 키보드 접근성이란 무엇입니까?

마우스 없이 Tab, Shift+Tab, Enter, Space, 방향키 등을 이용해 주요 기능을 사용할 수 있도록 하는 것입니다.

focus(초점) 순서와 시각적 focus(초점) indication이 특히 중요합니다.

Q171. tabindex=0과 -1의 차이는?

tabindex="0"은 자연스러운 tab 순서에 요소를 포함하고, tabindex="-1"은 Tab으로 직접 접근하지 않지만 JavaScript로 focus를 이동할 수 있습니다.

양수 tabindex는 인위적인 순서를 만들어 일반적으로 피하는 것이 좋습니다.

Q172. focus와 focus-visible의 차이는?

:focus(초점)는 요소가 focus를 가진 모든 상황에 적용되고, :focus-visible은 브라우저가 키보드 탐색처럼 focus(초점) 표시가 필요하다고 판단하는 경우에 스타일을 적용합니다.

기본 outline을 제거한다면 대체 focus(초점) style을 반드시 제공해야 합니다.

Q173. ARIA란 무엇입니까?

HTML만으로 충분히 표현되지 않는 UI의 역할·상태·관계를 accessibility(접근성) tree에 전달하는 attribute(속성) 체계입니다.

가능하면 native HTML(기본 HTML 요소) 요소를 우선하고, ARIA를 많이 쓰는 것 자체가 목표는 아닙니다.

Q174. role="button"을 div에 붙이면 button과 같습니까?

의미상 button 역할을 전달할 수는 있지만 native button이 기본 제공하는 focus(초점), Enter/Space 동작 등을 직접 구현해야 할 수 있습니다.

가능하면 실제 <button>을 사용하는 것이 좋습니다.

Q175. aria-expanded는 무엇입니까?

accordion, dropdown 등이 펼쳐졌는지 접혀 있는지 보조기술에 전달하는 상태 속성입니다.

UI(사용자 인터페이스) 상태와 함께 동기화해야 합니다.

Q176. aria-controls는 무엇입니까?

현재 control이 어떤 요소를 제어하는지 대상 요소의 ID로 연결합니다.

Q177. aria-label과 aria-labelledby의 차이는?

aria-label은 직접 문자열로 accessible name을 제공하고, aria-labelledby는 기존 DOM(문서 객체 모델) 텍스트 요소의 ID를 참조합니다.

Q178. aria-hidden=true는 무엇입니까?

해당 요소와 하위 내용을 accessibility(접근성) tree에서 숨깁니다.

focus(초점) 가능한 interactive element에 무분별하게 적용하면 접근성 문제가 생길 수 있습니다.

Q179. Skip Link가 무엇입니까?

키보드 사용자가 반복되는 header/navigation을 건너뛰고 바로 main content로 이동할 수 있게 하는 링크입니다.

Q180. Heading(제목 계층) 구조가 왜 중요합니까?

문서의 논리적 정보 계층을 나타내며, 스크린리더 사용자도 heading을 이용해 페이지를 빠르게 탐색할 수 있습니다.

글자 크기는 CSS에서 정하고 heading level은 의미 구조로 정해야 합니다.

Q181. Modal(모달 창) 접근성에서 중요한 것은?

dialog(대화상자) semantics, accessible name(접근 가능한 이름), 열렸을 때 focus(초점) 이동, 필요한 경우 focus(초점) trap(초점 가두기), Escape 닫기, 닫은 후 원래 trigger로 focus(초점) 복귀, background interaction(상호작용) 제한 등을 고려합니다.

Q182. 웹접근성 자동검사만으로 충분합니까?

아닙니다. Lighthouse나 axe는 규칙 기반 오류를 찾는 데 유용하지만 alt의 문맥 적절성, 실제 키보드 흐름, 스크린리더 사용성까지 모두 판단하지는 못합니다.

자동검사 + 사람 검토가 필요합니다.

Q183. 웹표준이란 무엇입니까?

특정 브라우저나 환경에 종속되지 않도록 HTML, CSS, JavaScript 등의 웹 기술을 표준 사양에 맞춰 사용하는 것입니다.

웹표준과 접근성은 관련이 있지만 같은 개념은 아닙니다.

Q184. HTML Validator는 왜 사용합니까?

화면만 봐서는 발견하기 어려운 잘못 닫힌 태그, 잘못된 attribute(속성), 문법 오류 등을 찾는 데 도움이 됩니다.

Valid HTML이라고 해서 UX·접근성·성능까지 모두 좋다는 뜻은 아닙니다.

Q185. lang 속성은 왜 중요합니까?

문서의 기본 언어를 보조기술과 검색엔진에 전달합니다.

HTML
<html lang="ko">

Q186. 크로스브라우징이 무엇입니까?

지원 대상 브라우저에서 기능과 주요 UI가 의도한 수준으로 일관되게 동작하도록 확인하고 대응하는 작업입니다.

모든 브라우저에서 픽셀까지 완전히 동일하게 만드는 것이 목표는 아닙니다.

Q187. 브라우저마다 화면이 다른 이유는?

렌더링 엔진 차이, user-agent style(브라우저 기본 스타일), CSS feature 지원, form control 표현, font rendering(글꼴 렌더링), OS 차이 등이 있습니다.

Q188. Vendor Prefix란 무엇입니까?

브라우저별 실험적/과거 구현을 지원하기 위해 사용되는 prefix입니다. 예: -webkit-.

필요 여부를 확인하지 않고 무조건 붙이는 것이 아니라 지원 브라우저와 feature compatibility를 확인해야 합니다.

Q189. Progressive Enhancement란?

기본 콘텐츠와 핵심 기능은 넓은 환경에서 사용할 수 있게 만들고, 지원되는 환경에서는 더 향상된 기능을 추가하는 접근입니다.

Q190. Graceful Degradation이란?

최신 환경에서는 완전한 기능을 제공하되, 구형 환경에서는 일부 기능이 줄어들더라도 핵심 기능은 사용할 수 있도록 하는 접근입니다.

Progressive Enhancement와 출발 방향이 반대라고 이해할 수 있습니다.

Q191. Safari에서만 CSS가 깨지면 어떻게 합니까?

먼저 computed style과 layout을 확인하고 feature support(기능 지원 여부), flex/grid sizing, viewport(화면 표시 영역) unit, form style, 브라우저 버그 가능성을 단계적으로 좁힙니다.

바로 “Safari 버그”라고 단정하지 않고 최소 재현 코드를 만들어 문제를 분리하는 것이 좋습니다.

Q192. 웹 성능이 왜 중요합니까?

로딩과 interaction이 느리면 사용성이 떨어지고 이탈 가능성이 높아집니다.

퍼블리셔는 이미지 크기, CSS/JS loading, DOM(문서 객체 모델) 구조, font, animation(애니메이션) 등 frontend(프론트엔드) 자원 최적화에 기여할 수 있습니다.

Q193. Lighthouse는 무엇입니까?

브라우저 기반 자동 진단 도구로 Performance(성능), Accessibility(접근성), Best Practices(권장 사례), SEO(검색엔진 최적화) 등을 분석합니다.

Lighthouse(웹 품질 자동 진단 도구) 점수가 실제 사용자 경험 전체를 의미하는 것은 아닙니다.

Q194. Core Web Vitals를 설명해 주세요.

대표적으로:

  • LCP(최대 콘텐츠 표시 시간): 주요 콘텐츠가 얼마나 빨리 보이는가
  • INP(상호작용 반응성 지표): 사용자 interaction에 얼마나 빠르게 반응하는가
  • CLS(누적 레이아웃 이동): 레이아웃이 얼마나 안정적인가

정확한 수치 암기보다 무엇을 측정하는지 이해하는 것이 우선입니다.

Q195. LCP를 개선하려면?

hero/LCP(최대 콘텐츠 표시 시간) 이미지 최적화, critical resource(핵심 리소스) 우선 제공, render-blocking resource(렌더링 차단 리소스) 감소, font/image loading 최적화, 서버 응답 개선 등을 고려할 수 있습니다.

Q196. CLS가 발생하는 대표 원인은?

이미지 width/height 미지정, 동적 콘텐츠 삽입, 광고 영역, webfont 교체 등으로 공간이 뒤늦게 바뀌는 경우입니다.

이미지에 width/height 또는 aspect-ratio를 제공하면 도움이 됩니다.

Q197. 이미지 최적화 방법은?

실제 표시 크기에 맞는 이미지 사용, WebP/AVIF 같은 효율적 포맷 검토, responsive(반응형) image(반응형 이미지), viewport(화면 표시 영역) 밖 이미지 lazy loading(지연 로딩), width/height 또는 aspect-ratio 확보 등을 고려합니다.

단 LCP(최대 콘텐츠 표시 시간) hero 이미지는 lazy loading을 신중하게 판단해야 합니다.

Q198. Lazy Loading이 무엇입니까?

당장 필요하지 않은 resource의 로딩을 나중으로 미루는 방식입니다.

이미지에서는 loading="lazy"를 사용할 수 있지만, 첫 화면 핵심 이미지는 오히려 성능을 악화시킬 수 있어 주의합니다.

Q199. CSS가 render blocking인 이유는?

브라우저가 올바른 화면을 그리기 전에 CSSOM이 필요하므로 주요 stylesheet가 initial rendering을 지연시킬 수 있습니다.

Q200. @import가 성능상 문제가 될 수 있는 이유는?

CSS가 다른 CSS를 연쇄적으로 발견해 불러오면 resource(리소스) discovery가 늦어질 수 있습니다.

가능하면 직접 <link(링크)>로 필요한 stylesheet를 로드하거나 bundling 전략을 사용합니다.

Q201. Reflow와 Repaint의 차이는?

Reflow(레이아웃 재계산)/Layout은 요소의 위치·크기 geometry를 다시 계산하는 것이고, Repaint는 layout은 같지만 픽셀 표현을 다시 그리는 과정입니다.

Q202. Layout(레이아웃) Thrashing이 무엇입니까?

JavaScript에서 layout(레이아웃) 값을 읽고 쓰는 작업을 반복해 브라우저가 강제로 layout(레이아웃) 계산을 계속 수행하는 문제입니다.

DOM(문서 객체 모델) 읽기와 쓰기를 묶고 불필요한 layout(레이아웃) trigger를 줄이는 것이 좋습니다.

Q203. SEO란 무엇입니까?

검색엔진이 페이지의 콘텐츠와 구조를 잘 이해하고 적절한 검색결과로 제공할 수 있도록 사이트를 구성하는 작업입니다.

퍼블리셔는 title, heading, semantic(의미론적) markup, meta description, link(링크) 구조, alt, 성능 등에 기여할 수 있습니다.

Q204. title이 왜 중요합니까?

브라우저 탭 식별, 검색결과, 접근성 context에 사용되는 중요한 metadata입니다.

페이지별로 고유하고 구체적인 title을 작성하는 것이 좋습니다.

Q205. meta description이 ranking을 직접 올립니까?

description 하나만으로 검색순위가 결정되지는 않습니다.

검색결과 snippet에 활용될 수 있으므로 페이지 내용을 명확히 설명하는 것이 중요합니다.

Q206. alt를 SEO(검색엔진 최적화) 키워드 채우기로 써도 됩니까?

안 됩니다. alt는 우선 이미지의 의미를 사용자에게 전달하기 위한 접근성 정보입니다.

검색엔진에도 도움이 될 수 있지만 키워드 stuffing 용도로 작성하면 안 됩니다.

Q207. Canonical이 무엇입니까?

유사하거나 중복된 URL이 있을 때 검색엔진에 대표 URL을 알려주는 link(링크) relation입니다.

Q208. Sitemap과 robots.txt의 차이는?

Sitemap은 검색엔진에 주요 URL 목록을 알려주고, robots.txt는 crawler의 접근 범위를 안내합니다.

robots.txt는 보안 수단이 아니며 민감정보 보호에 사용하면 안 됩니다.

Q209. Git이 무엇입니까?

코드와 파일의 변경 이력을 관리하는 분산 버전관리 시스템입니다.

어떤 시점에 무엇을 바꿨는지 추적하고 여러 사람이 각자 branch에서 작업한 뒤 변경사항을 통합할 수 있습니다.

Q210. Git과 GitHub의 차이는?

Git은 버전관리 도구이고, GitHub는 Git repository를 호스팅하고 협업 기능을 제공하는 서비스입니다.

Q211. Working Directory(작업 디렉터리), Staging Area(스테이징 영역), Repository(저장소) 차이는?

현재 수정 중인 파일은 Working Directory(작업 디렉터리), git add로 다음 commit에 포함할 변경을 올리는 곳이 Staging Area(스테이징 영역), git commit(변경 이력 저장)으로 기록된 이력이 Local Repository입니다.

git push(원격 저장소 전송)로 remote(원격 저장소) repository에 전송합니다.

Q212. commit과 push의 차이는?

commit은 local(로컬) repository에 변경 이력을 기록하고, push는 local(로컬) commit을 remote(원격 저장소) repository로 전송합니다.

Q213. pull과 fetch의 차이는?

fetch는 remote(원격 저장소) history를 가져오지만 현재 branch에 자동 통합하지 않고, pull은 일반적으로 fetch(원격 변경 조회·가져오기) 후 merge(병합)/rebase(기준 재배치) 형태로 현재 branch에 반영합니다.

Q214. branch란 무엇입니까?

서로 독립적인 작업 흐름을 만들기 위한 포인터입니다.

Q215. merge(병합) conflict는 왜 생깁니까?

Q216. conflict가 나면 어떻게 해결합니까?

충돌 파일에서 양쪽 변경의 의도를 확인하고 필요한 최종 코드를 직접 결정해 conflict(충돌) marker를 제거합니다.

이후 UI(사용자 인터페이스)/기능을 테스트하고 add와 commit을 진행합니다.

Q217. reset과 revert의 차이는?

reset은 branch(분기 작업선) pointer를 과거 상태로 이동해 history를 재작성할 수 있습니다.

revert는 기존 commit의 변경을 반대로 적용하는 새 commit을 만듭니다.

이미 팀원이 pull한 공유 branch에서는 revert가 더 안전한 경우가 많습니다.

Q218. git status와 git diff를 왜 자주 봅니까?

git status는 수정·staged(커밋 대기 상태)·untracked(추적되지 않음) 파일과 branch(분기 작업선) 상태를 확인하고, git diff(변경 차이)는 실제 코드 변경 내용을 비교합니다.

문제가 생겼을 때 현재 상태를 파악하는 기본 도구입니다.

Q219. 좋은 commit(변경 이력 저장) 단위란 무엇입니까?

한 commit이 하나의 논리적 변경 목적을 갖는 것이 좋습니다.

기능 추가와 관계없는 대규모 formatting 수정이 한 commit에 섞이면 review와 rollback이 어려워질 수 있습니다.

그 이후 배치 작업은 “완료”라는 문장을 믿지 않고 예상 파일 수와 실제 파일 수를 비교하는 절차를 넣었습니다.

Q247. 또 다른 완료보고 오류 사례는?

필터바를 전체 페이지에서 제거했다고 보고했지만 실제로 4개 파일에 남아 있었고, 신규 JS 4종을 추가했다고 보고했지만 실제로는 8종이 생성돼 있었습니다.

많이 보고하든 적게 보고하든 보고와 실물이 일치하는지 확인해야 한다는 결론은 같았습니다.

Q248. AI 검수에 AI를 쓰는 게 신뢰할 수 있습니까?

검색, count, 반복 대조 같은 실행 작업은 AI를 활용할 수 있습니다.

대신 무엇을 검사할지 기준을 정하고, 결과가 요구사항을 충족하는지 판단하고, 반려하는 책임은 사람이 가져야 합니다.

또 JW에서 자동 분석 결과에 누락이 있었던 경험 때문에 AI가 만든 검수 결과도 다른 방법으로 다시 대조했습니다.

Q249. 본인이 직접 세지 않았는데 359건을 믿을 수 있습니까?

모든 항목을 눈으로 하나씩 센 것이 아니라 README의 일자별 검수 기록과 repository(저장소) 상태를 기반으로 집계하고 다시 대조했습니다.

그래서 문서에서도 수치의 측정 기준과 정정 이력을 남기려고 했습니다.

Q250. 숫자가 잘못된 적도 있습니까?

있습니다.

이전 버전에서 hardcoded(값을 직접 입력한) color 수치, 페이지 수, creator(제작자) 범위, breakpoint(분기점) 정의 등을 실제 repository(저장소) 기준으로 재측정하면서 정정했습니다.

그 경험 이후 문서에 적힌 숫자 자체도 검수 대상이라는 원칙을 만들었습니다.

Q251. 강의 상세를 152개 다 만들지 않은 이유는?

구조가 동일하고 내용만 바뀌는 페이지를 152번 복제해도 추가로 증명되는 퍼블리싱 역량이 없고 코드 중복만 크게 늘어난다고 판단했습니다.

그래서 대표 상세 1종을 구현하고 강의 카드에서 해당 페이지로 연결되는 링크가 정상인지 검증했습니다.

Q252. JW에서는 392개 만들고 HOOT UP에서는 반복을 줄인 이유는?

JW를 만들면서 반복 구조의 유지보수 비용을 직접 경험했기 때문입니다.

JW에서는 규모 자체를 경험하는 것이 학습 목표였고, 그 경험을 반영해 HOOT UP에서는 구조가 같고 콘텐츠만 다른 반복은 줄이고 링크·컴포넌트 일관성 검증으로 방향을 바꿨습니다.

Q253. HOOT UP에서 본인이 설계한 것은 무엇입니까?

브랜드·콘텐츠 구조, 152강 카탈로그, Figma 변수 체계, 접근성 요구사항, PRD, 검수 기준, 구조 반려 등을 담당했습니다.

HTML/CSS/JS 생성 자체는 AI가 담당했습니다.

Q254. HOOT UP에서 Figma prototype까지 만들었습니까?

현재는 JW Anderson은 prototype까지 연결했지만 HOOT UP은 화면 설계와 디자인 시스템까지 진행하고 전체 prototype은 만들지 못했습니다.

HOOT UP은 PRD와 구현 기준을 먼저 확정하고 AI 구현 및 검수 workflow를 실험하는 데 우선순위를 뒀습니다.

추후에는 대표 사용자 journey 중심의 prototype을 보완할 수 있다고 생각합니다.

Q255. 사전 PRD와 사후 문서를 구분한 이유는?

처음 계획과 실제 구현이 어떻게 달라졌는지 설명할 수 있도록 하기 위해서입니다.

착수 전 요구사항을 먼저 고정하고, 구현 중 변경된 것은 변경 ID·결함 ID로 남긴 뒤 최종 구현 결과를 반영한 문서를 별도로 정리했습니다.

Q256. Defect와 Change의 차이는?

Defect는 원래 요구사항을 충족하지 못한 문제이고, Change는 기존 요구사항을 의도적으로 바꾼 결정이라고 구분했습니다.

Q257. 404 링크가 3,389건이나 있었다는 게 무슨 뜻입니까?

개별 링크 3,389개를 사람이 각각 잘못 만든 것이 아니라 공통 경로 규칙 문제 때문에 반복 링크가 한꺼번에 잘못된 상태였습니다.

공통 규칙을 수정하자 전체에서 해결됐고, 반복 구조에서는 개별 수정보다 생성 규칙을 고치는 것이 중요하다는 사례였습니다.

Q258. Lighthouse(웹 품질 자동 진단 도구) 접근성 100이면 완벽합니까?

아닙니다.

자동검사에서 탐지 가능한 규칙을 통과했다는 의미일 뿐 실제 키보드 탐색, 스크린리더 흐름, alt 문맥 적절성 등은 별도 사람 검증이 필요합니다.

Q259. hardcoded(값을 직접 입력한) color를 끝까지 0으로 못 만든 이유는?

일괄적인 primitive(원시값) token(기초 토큰) 치환보다 semantic(의미론적) 역할 판단이 필요한 색상이 계속 발생했습니다.

자동 변환만으로 해결하기 어려운 부분이 있어 미완료 상태를 숨기지 않고 공개했습니다.

Q260. semantic(의미론적) token(의미 기반 토큰) 전환이 처음 7%에서 정체된 이유는?

새 component가 생길 때 계속 raw token을 직접 참조했기 때문입니다.

token을 선언하는 것만으로 실제 사용 정책이 자동으로 지켜지지 않아, 이후 semantic(의미론적) alias(의미 기반 별칭) 사용 자체를 검수 기준으로 추가했습니다.

Q261. AI에게 규칙을 한 번 말했는데 왜 계속 안 지켜졌습니까?

새 component(컴포넌트) 생성 시 기존 잘못된 패턴을 다시 만들 수 있었기 때문입니다.

중요한 규칙은 prompt(프롬프트·지시문) 한 번으로 끝내지 않고 PRD, component(컴포넌트) pattern, acceptance criteria(완료 승인 기준), 검수 조건 같은 구조로 반복 강제해야 한다고 느꼈습니다.

Q262. AI에게 지시할 때 어떻게 했습니까?

원하는 결과뿐 아니라 깨지면 안 되는 조건을 함께 명시했습니다.

예를 들어 “썸네일 hover(마우스 올림 상태) 시 1.3배 확대”만 말하지 않고 “감싸는 card layout의 크기는 변하면 안 된다”는 constraint까지 같이 줬습니다.

Q263. AI의 의견을 받아들인 적도 있습니까?

있습니다.

중요한 것은 누가 제안했느냐가 아니라 근거가 맞는지 확인하는 것이라고 생각합니다.

예를 들어 <main> 사용과 관련해 제가 처음 생각한 방식보다 AI가 제시한 표준 근거가 더 타당해 원안을 유지한 사례가 있습니다.

Q264. 사람이 항상 AI보다 잘 판단한다고 생각합니까?

아닙니다. 사람도 틀릴 수 있고 실제 프로젝트에서 저도 잘못 측정하거나 판단한 부분이 있었습니다.

사람과 AI 중 누가 더 우월하다는 관점보다 서로의 결과를 실제 산출물과 근거로 검증하는 workflow가 더 중요하다고 생각합니다.

Q265. AI 시대 웹퍼블리셔의 역할은 무엇이라고 봅니까?

반복적인 마크업 생산은 AI 비중이 커질 수 있습니다.

대신 디자인 시안과 요구사항을 해석하고 반응형, 접근성, 기존 코드 영향, 유지보수성을 판단하고 AI 산출물을 검증하는 역할은 더 중요해질 수 있다고 생각합니다.

저는 직접 구현 기본기를 유지하면서 AI를 생산성 도구로 활용하는 방향으로 준비하고 있습니다.

Q266. HOOT UP에서 가장 큰 성과는?

164페이지라는 숫자보다 완료보고를 그대로 믿지 않고 실제 repository(저장소) 상태를 검사하는 검수 절차를 만든 것입니다.

Q267. HOOT UP에서 가장 큰 실패는?

문서의 수치를 AI 보고와 함께 믿었던 시점이 있었고, 나중에 재측정하면서 일부 집계가 잘못됐다는 것을 발견했습니다.

그 이후 문서에 쓰인 숫자 자체도 검수 대상으로 바꿨습니다.

Q268. HOOT UP을 다시 만든다면 무엇을 바꾸겠습니까?

대표 사용자 journey는 Figma prototype으로 먼저 연결하고, semantic(의미론적) token(의미 기반 토큰) 정책과 accessibility(접근성) checklist를 초기 구현 단계에서 더 강하게 고정할 것입니다.

또 모든 AI 완료보고에 처음부터 정량 acceptance criteria를 붙이겠습니다.

PART 8코드 리뷰·실기 면접

Q269. HTML에서 div+onclick을 a/button으로 바꿔야 하는 이유는?

div는 기본 interactive element가 아니므로 키보드 focus와 기본 동작을 직접 구현해야 합니다.

페이지 이동은 <a>, 현재 페이지 기능 실행은 <button>을 사용하면 브라우저와 보조기술이 기본 역할을 이해합니다.

Q270. 로그인 폼의 대표적인 마크업 문제를 찾아보세요.

대표 체크:

  • form 사용 여부
  • label 연결
  • email/password input type
  • name 속성
  • autocomplete
  • submit button
  • placeholder가 label을 대체하지 않는지
  • 페이지 이동 기능은 anchor인지
HTML
<form>
  <label for="email">이메일</label>
  <input id="email" type="email" autocomplete="email" required>
  <button type="submit">로그인</button>
</form>

Q271. 링크 안에 button이 들어간 카드 구조의 문제는?

interactive 요소 안에 또 다른 interactive 요소가 중첩됩니다.

상품 상세 링크와 즐겨찾기 버튼처럼 서로 다른 동작은 구조적으로 분리해야 합니다.

Q272. width:100% + padding(안쪽 여백) 때문에 부모보다 넓어지는 이유는?

기본 box-sizing: content-box에서는 width가 content(콘텐츠) 영역만 의미하고 padding과 border가 추가되기 때문입니다.

box-sizing:border-box로 지정하면 지정 width 안에 padding(안쪽 여백)/border가 포함됩니다.

Q273. Flex(플렉스) 텍스트 말줄임이 안 될 때 무엇을 봅니까?

ellipsis(말줄임) 기본 조건인 overflow:hidden, white-space:nowrap, text-overflow:ellipsis(말줄임)를 확인하고, flex item이라면 min-width:0이 필요한지 봅니다.

Q274. Grid(그리드) 4열 코드를 더 재사용성 있게 작성하려면?

CSS
.products {
  display:grid;
  grid-template-columns:repeat(4,minmax(0,1fr));
}

콘텐츠 기준 자동 열 수가 필요하다면 auto-fit + minmax()도 고려할 수 있습니다.

다만 디자인 요구가 정확히 4/2/1이라면 breakpoint(분기점) 방식이 더 적절할 수 있습니다.

Q275. 반응형에서 고정 width 1200px/375px의 문제는?

특정 기기 폭에만 맞춰져 다양한 viewport에서 깨질 수 있습니다.

max-width, %, min(), clamp(), padding(안쪽 여백) 등을 이용해 유연하게 설계하는 것이 좋습니다.

Q276. 100vw + padding이 overflow를 만들 수 있는 이유는?

content-box에서 padding이 추가되고, 100vw가 scrollbar 폭까지 포함할 수 있어 viewport보다 넓어질 수 있습니다.

가능하면 width:100%와 box-sizing:border-box가 자연스러운지 검토합니다.

Q277. 강한 ID selector(선택자) 때문에 active class가 안 먹는 문제를 어떻게 해결합니까?

!important로 덮기보다 불필요하게 높은 specificity를 낮추고 selector(선택자) 구조를 정리합니다.

CSS
.nav a { color:black; }
.nav a.active { color:red; }

Q278. :is()로 중복을 합칠 때 무엇을 검증해야 합니까?

specificity와 기존 cascade(계단식 우선순위)/override(덮어쓰기) 관계가 변하지 않는지 확인해야 합니다.

단순 line 감소보다 regression(회귀 오류) 방지가 우선입니다.

Q279. querySelector 결과가 null인 대표 원인은?

selector(선택자) 오타, 해당 페이지에 요소가 없음, DOM(문서 객체 모델) 파싱 전에 script가 실행됨입니다.

원인을 먼저 확인하고 의도적으로 요소가 없는 페이지라면 존재 여부 guard를 둘 수 있습니다.

Q280. head에서 script를 실행해 DOM(문서 객체 모델) 요소가 null이면 어떻게 합니까?

script에 defer를 붙이거나 body 끝에 배치해 DOM(문서 객체 모델) 파싱 이후 실행되도록 합니다.

Q281. for(var i...) + setTimeout에서 3,3,3이 나오는 이유는?

var가 block(블록) scope가 아니고 callback이 실행될 때 loop가 끝나 i가 3이기 때문입니다.

let을 사용하면 각 반복마다 block-scoped binding이 생겨 0,1,2를 얻을 수 있습니다.

Q282. 동적 버튼에 기존 click handler가 안 붙으면?

초기 시점 NodeList에만 listener가 등록됐을 수 있습니다.

공통 부모에 event delegation을 적용합니다.

Q283. JS에서 여러 style을 직접 바꾸는 코드를 개선하려면?

class로 상태만 변경하고 CSS에서 표현을 관리합니다.

JS
menu.classList.toggle('is-open');

Q284. Menu 토글 접근성에서 추가할 것은?

aria-expanded와 aria-controls를 사용하고 시각 상태와 접근성 상태를 함께 갱신합니다.

Q285. Modal(모달 창) 코드리뷰 시 무엇을 봅니까?

dialog(대화상자) semantics, accessible name(접근 가능한 이름), focus(초점) 이동, focus(초점) trap(초점 가두기) 필요 여부, Escape, 닫은 후 trigger focus(초점) 복귀, background interaction(상호작용) 관리 등을 봅니다.

Q286. 사용자 입력을 innerHTML에 넣는 코드의 문제는?

XSS(교차 사이트 스크립팅) 위험이 있습니다.

plain text라면 textContent를 사용하고, markup이 필요하다면 DOM(문서 객체 모델) API로 안전하게 요소를 생성하거나 sanitization이 필요합니다.

Q287. fetch(원격 변경 조회·가져오기) 코드리뷰에서 response.ok를 왜 봅니까?

HTTP 404/500이 fetch(원격 변경 조회·가져오기) Promise를 자동 reject시키지 않을 수 있기 때문입니다.

JS
if(!response.ok) throw new Error(...)

Q288. jQuery arrow callback에서 $(this)가 안 되는 이유는?

arrow function은 자체 this를 만들지 않기 때문에 클릭 요소를 가리키지 않을 수 있습니다.

function(){ $(this)... } 또는 event.currentTarget을 사용합니다.

Q289. 이미지를 CSS로 300px로 줄이면 네트워크 용량도 줄어듭니까?

아닙니다. 3000×4000 이미지를 CSS로 300px로 표시해도 원본 파일 용량은 그대로 다운로드될 수 있습니다.

실제 표시 크기에 맞는 이미지와 responsive(반응형) image를 제공해야 합니다.

Q290. CLS를 줄이기 위해 이미지에서 무엇을 할 수 있습니까?

width/height 또는 aspect-ratio를 제공해 브라우저가 로딩 전에 공간을 확보하도록 합니다.

Q291. scroll 이벤트에서 top을 계속 바꾸는 코드의 문제는?

고빈도 이벤트에서 layout-related property를 계속 변경해 성능 비용이 커질 수 있습니다.

요구사항에 따라 CSS position:sticky, transform(변형), requestAnimationFrame, throttle, IntersectionObserver 등을 검토합니다.

Q292. Git에서 이미 공유된 잘못된 commit을 되돌릴 때?

이미 팀원이 pull한 shared branch라면 history를 함부로 reset하기보다 git revert(되돌림 커밋 생성)로 반대 변경을 새 commit으로 남기는 방법을 우선 검토합니다.

Q293. Git conflict(충돌) marker를 보면 어떻게 해결합니까?

양쪽 변경의 의도를 확인해 최종 코드를 결정하고 conflict(충돌) marker를 제거한 뒤 테스트하고 add/commit(변경 이력 저장) 합니다.

내 코드만 무조건 유지하지 않습니다.

Q294. AI가 “모든 .old-price 제거 완료”라고 했을 때 어떻게 검수합니까?

repository(저장소) 전체 검색으로 .old-price 잔존 여부를 확인하고, 제거 과정에서 마크업이 깨지지 않았는지 대표 페이지와 영향 페이지를 브라우저에서 확인합니다.

필요하면 HTML validation이나 자동검사를 추가합니다.

AI의 “완료”는 검수 결과가 아니라 검수 시작점으로 봅니다.

Q295. primitive(원시값) token으로 바뀌면 design token(디자인 토큰) 적용 완료라고 볼 수 있습니까?

반드시 그렇지는 않습니다.

예를 들어 color: var(--gray-900)은 값 중앙화는 됐지만 semantic(의미론적) role이 드러나지 않을 수 있습니다.

--text-primary: var(--gray-900) 같은 semantic(의미론적) alias를 두고 component가 이를 참조하는 구조가 역할 변경에 더 유연할 수 있습니다.

Q296. Lighthouse(웹 품질 자동 진단 도구) Accessibility(접근성) 100이면 문제 없습니까?

아닙니다. 자동검사가 발견할 수 있는 항목을 통과했다는 의미일 뿐입니다.

alt 문장 적절성, keyboard 흐름, modal focus(초점), 실제 screen reader(화면 낭독기) 경험은 별도 검증이 필요합니다.

Q297. 상품 카드 종합 코드리뷰에서 어떤 순서로 봅니까?

HTML: 의미 → interactive 중첩 → heading → alt → 접근성 CSS: layout(레이아웃) → box model → position/stacking → overflow → ellipsis(말줄임) → responsive(반응형) JS: selector(선택자) → event → bubbling → target(실제 이벤트 발생 요소)/currentTarget(현재 이벤트 처리 요소) → state(상태) → ARIA(접근성 보조 속성 체계) jQuery: function/arrow → this → delegation → traversal(요소 탐색)

정답 개수보다 이런 스캔 순서를 갖는 것이 실무적으로 중요합니다.

Q298. 실기에서 모르는 문제를 만나면 어떻게 대응합니까?

없는 API를 만들어내지 않고 “정확한 API(응용프로그램 인터페이스) 이름은 지금 기억나지 않지만, 먼저 DevTools에서 ○○를 확인하고 원인을 이렇게 좁히겠습니다”라고 문제 해결 순서를 설명합니다.

기술면접은 정답뿐 아니라 디버깅 사고를 봅니다.
